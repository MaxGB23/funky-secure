# Empirical evidence E1–E8 — RFC 15.5

Pre-implementation validation for `funky-secure` (RFC revision 2, v1.1). Every row below is an
observation, not a plan. Nothing outside `.tmp/` was written; the RFC was not modified.

- Collected: **2026-10-23, 21:48–22:05 UTC** (all ages in minutes are computed at run time from the
  registry `time` map and quoted with the timestamp they were computed at).
- Host: Windows, Git Bash, `node v24.16.0`, `pnpm 12.3.4` (parent-measured: `where pnpm` →
  `C:\Users\cb147\AppData\Local\pnpm\bin\pnpm` and `...\bin\pnpm.cmd`; the shim delegates to
  `...\pnpm\global\v11\557a16cc51f818d142da6cabdc92990972c46d60721da61794cda49f5c7e27d2\node_modules\@pnpm\exe\pnpm.exe`,
  which is **not** on `PATH`).

## 0. Method, isolation and network use

**Network was used, deliberately and only for these purposes.** All pnpm resolution below is live
against `https://registry.npmjs.org/`; the documented pnpm default was read from the official docs
source on GitHub (`https://raw.githubusercontent.com/pnpm/pnpm.io/main/docs/settings.md` and
`.../docs/settings/dependency-resolution.md`, saved as `.tmp/evidence/e1/pnpm-settings.html` and
`.tmp/evidence/e1/pnpm-docs-dependency-resolution.md`). No other host was contacted, and no token,
cookie or credential was read or printed.

**Isolation, after the parent's reported bug** (a fixture inheriting `../pnpm-lock.yaml`):

```
.tmp/evidence/
  bin/penv.sh    # pins HOME, USERPROFILE, APPDATA, LOCALAPPDATA, XDG_*, npm_config_userconfig
  bin/probe.sh   # one fresh fixture per run; prints cwd, parents, command, exit, files, workspace
  bin/seed.sh    # same, but the caller seeds package.json / pnpm-workspace.yaml first
  bin/age.mjs    # prints published time + ageMinutes + dependency lists for one spec
  home/          # the dedicated clean HOME (created before any run)
  home2/         # second clean HOME used only for the user-level ~/.npmrc probe (E8)
  e1/ … e8/      # one directory per probe; each fixture checks its own parents before running
```

Every run prints its ancestors; none of them ever contained `pnpm-lock.yaml` or
`pnpm-workspace.yaml` except the fixture itself. The harness refuses to reuse an existing fixture
directory (`REFUSING: <dir> exists`). `%LOCALAPPDATA%\pnpm\config\config.yaml` on the real machine
(`minimumReleaseAge: 4320`, `ignoreScripts: true`) is never reachable from these runs because
`LOCALAPPDATA`/`XDG_CONFIG_HOME` are repointed at `.tmp/evidence/home`.

## 4. E3 — `git check-ignore --no-index --stdin -z`

Fixture `.tmp/evidence/e3/repo` (`git init`), root `.gitignore`:

```
# ignore env
.env
!.env
```

`sub/.gitignore`:

```
# nested
*.env
!keep.env
```

Per-path runs, one path per invocation (verdict probe, **no** `-v`):

```
input=[.env] exit=1 stdout=[]
input=[.env.example] exit=1 stdout=[]
input=[sub/.env] exit=0 stdout=[sub/.env,]
input=[sub/keep.env] exit=1 stdout=[]
input=[sub/deep/.env] exit=0 stdout=[sub/deep/.env,]
input=[nope.txt] exit=1 stdout=[]
```

Batch form, same fixture:

```
$ printf '%s\0' .env .env.example sub/.env sub/keep.env sub/deep/.env | git check-ignore --no-index --stdin -z | tr '\0' '\n'
sub/.env
sub/deep/.env
batch exit=0
```

Negations are honored (root `.env` is *not* ignored because `!.env` is the last match; `sub/keep.env`
is *not* ignored), and the **nested** `sub/.gitignore` applies to `sub/.env` and — for its `*.env`
pattern — to `sub/deep/.env`.

The trap, with `-v`:

```
input=[.env] exit=0 raw=[.gitignore|3|!.env|.env|]
input=[sub/keep.env] exit=0 raw=[sub/.gitignore|3|!keep.env|sub/keep.env|]
```

A negated path is reported as a *match* with exit `0` when `-v` is passed. Without `-v` the contract
is unambiguous: exit `0` = ignored, exit `1` = not ignored (including negated).

## 5. E4 — `git ls-files -z -- ':(glob)**/.env*'` on win32

Fixture `.tmp/evidence/e4/repo` (no ignore rules): `.env`, `.env.example`, `sub/.env`,
`sub/.env.local`, `sub/deep/.env`, `sub/deep/keep.txt`, all `git add -A`.

```
$ git ls-files -z -- ':(glob)**/.env*' | tr '\0' '\n'
.env
.env.example
sub/.env
sub/.env.local
sub/deep/.env
exit=0

$ git ls-files -- ':(glob)*.env*'
.env
.env.example

$ git ls-files -- ':(glob)**/.env'
.env
sub/.env
sub/deep/.env

$ git ls-files -- '**/.env*'          # no magic: root file is NOT matched
sub/.env
sub/.env.local
sub/deep/.env
```

The command works on win32 and matches root **and** nested paths. It also matches `.env.example`,
so R6's template exclusion list (`.env.example`, `.env.sample`, `.env.template`, `.env.dist`,
`.env.test.example`) is load-bearing, and `:(glob)` magic is required for the root file.

### 7.1 Shape-by-shape verdict for a purely line-based scanner

| shape | line-based outcome | why |
|---|---|---|
| `- name: X` then `uses: …` on the next line (the dominant real shape) | **missed** by any regex anchored on `- uses:` | 0 hits in both samples for naive A |
| dash alone, keys on following lines (`-\n  name:\n  uses:`) | caught only by the loose form; the step's start is ambiguous | line 11 in sample B is attributed to whatever preceded it |
| `uses: owner/repo@<sha> # v4.2.2` | ref captured **with** the comment (`… # v4.2.2`) | comment stripping must be quote-aware, and the comment is evidence, not part of the ref |
| `uses: "owner/repo@<sha>"` | ref captured **with** the quotes (`"actions/cache@…"`) | must unquote before validating 40 hex |
| `run: \|` block scalar containing `uses: …` text | **false positive** (`heredoc/decoy@deadbeef`) | block-scalar bodies are indented and are not steps |
| `with:` map key literally named `uses` | **false positive** (`not-an-action/ref@v9`) | the scanner has no idea it is inside `with` |
| `env: { USES: … }` | not a false positive here only because the key is uppercased | case sensitivity is an accident, not a guarantee |
| folded value `uses: >-` | **wrong ref** (`>-`) and the real value on the next line is lost | needs block-scalar joining, or `skip` |
| flow-style step `- { name: …, uses: … }` | **missed** | no line starts with `uses:` |
| `uses: ./.github/actions/local` | caught, then must be accepted (not pinnable) | needs an explicit local-action class |
| `docker://alpine:3.20` | caught, ref classification must treat `:` as a tag | rule: tag = finding |
| `docker://ghcr.io/owner/image@sha256:…` | caught, has both `@` and `:` | naive `rsplit('@')`/`split(':')` breaks; digest is the pass case |
| job-level `if: github.actor == 'dependabot[bot]'` | invisible to a `uses:` scanner | R9 needs job/step scoping, and `if:` may be `${{ }}` or a `>`/`\|` block |
| `uses: actions/checkout@v4 # tag, not a SHA` | caught, correctly a finding | trailing comment again part of the raw line |

### 7.2 What a minimal jobs→steps indentation reader must handle

1. Track indentation stack: `jobs:` (col 0) → job id (deeper) → `steps:` (deeper) → step (`-`) →
   step keys. Never assume 2 spaces; derive the step indent from the first `-` under `steps:`.
2. Treat both `- name: x` (inline first key) and `-` alone followed by an indented map as step starts.
3. Strip a trailing `# …` only when it is outside quotes and preceded by whitespace (so
   `uses: "owner/repo@sha" # v1` yields `owner/repo@sha`, and `docker://…@sha256:…` is untouched —
   note `#` inside a `sha256:` value never occurs, but `#` inside a `${{ }}` expression could).
4. Enter block-scalar mode on `key: |`, `key: >`, `key: |-`, `key: >-`, `key: |+`, `key: >+`,
   `key: |2`, … and skip every more-indented line until dedent. This is what kills the
   `heredoc/decoy` false positive.
5. Refuse (return `skip: unparseable-workflow`) on: anchors/aliases/merge keys (`&`, `*`, `<<:`),
   tabs, flow-style maps `{…}`/`[…]` at job or step level, multi-document `---`, and any indent
   jump that cannot be attributed to a job/step.
6. Job-level `if:` must be read at job scope (not step scope) and must accept both the raw form
   (`github.actor == 'dependabot[bot]'`) and the expression form
   (`${{ github.actor == 'dependabot[bot]' && … }}`).

## 10. Findings that affect the RFC

Ordered by blast radius. Each names the section whose assumption the measurement contradicts.

### F1 — §4.1, §1.3 fact 1 and R4 (8.2): the effective default 1440 is **not** in `pnpm config list --json`

R4 says the value is read "from the **effective** configuration reported by `pnpm config list --json`
(this merges global, workspace and environment, which is exactly the number pnpm will apply)". The
measurement says the opposite for the default case: on a clean machine the key is **absent** from
that listing (E1 §2.1, E2 §3) while pnpm applies **1440** anyway. A rule implemented literally would
read "no value" and either report `undefined` or compare `0 < 4320` and fail every healthy
repository — the exact stale-assertion failure mode the RFC exists to remove.

Required change: the effective value is
`config list --json`'s `minimumReleaseAge` **if present**, else pnpm's documented built-in default
(1440 for the 11/12 line, 0 before 11) reported as such — "pnpm built-in default" is itself evidence,
not a claim about a file. §4.1's "a value the manager already provides is reported" needs the
sentence "pnpm does not report a built-in default in `config list`; absence means *inherited*, never
*disabled*". The same applies to Appendix C's `minimumReleaseAge: 4320` reading: it is a *global*
setting, not a default.

### F2 — R4 (8.2) and W1 (11.2): writing `minimumReleaseAge` changes the **behaviour class**, not just the floor

The built-in default is **non-strict**: pnpm silently appends `minimumReleaseAgeExclude` entries to
`pnpm-workspace.yaml` and exits `0` — including under `CI=true`, i.e. it mutates the checkout during
a CI install (E1 §2.2). The moment `minimumReleaseAge` is *explicitly* configured — which is exactly
what W1 writes — `minimumReleaseAgeStrict` becomes `true` by default and the same setups fail:

- resolution → `ERR_PNPM_NO_MATURE_MATCHING_VERSION`, exit `1` (E1 §2.5);
- an existing lockfile containing a younger entry → `ERR_PNPM_MINIMUM_RELEASE_AGE_VIOLATION`,
  exit `1`, from the lockfile supply-chain verification (E1 §2.6).

So W1 is not "raise the number the manager already applies": it converts an auto-approve into a gate
and can turn a green CI red at the next install, with an error code the RFC never names. The plan
item's `reason` (11.2) and R4's remediation must say this, and must point at
`minimumReleaseAgeExclude` (the file pnpm itself already writes) as the escape hatch for a hotfix.
Note also that the lockfile verification does **not** enforce the built-in default (E1 §2.6, `n-…`):
"CI is already protected by default" is true for resolution and false for lockfile verification.

### F3 — R4's manual alternative (8.2) and §1.3 fact 3: `minimum-release-age` in `.npmrc` is ignored at every level, but `--location=project` still works because it writes `pnpm-workspace.yaml`

The literal condition the RFC attached to the manual alternative ("offered as a manual alternative
**only if** E8 proves that pnpm reads the value from a project `.npmrc`") **fails**: a project
`.npmrc`, a user `~/.npmrc` and `npm_config_userconfig` are all ignored for this key (E8). §1.3 fact
3 is confirmed for behaviour settings.

But `pnpm config set minimum-release-age 4320 --location=project` remains a correct remediation,
for a different reason: in pnpm 12 project config **is** `pnpm-workspace.yaml`, so the command writes
the very key W1 writes (E8). Consequences for the RFC:

- reword the guard as "`--location=project` writes `pnpm-workspace.yaml` in pnpm 12; `--location=global`
  writes the pnpm global `config.yaml`; an `.npmrc` is never involved";
- add one sentence to R4/docs: a hand-written `minimum-release-age` in `.npmrc` is **silently
  ignored** — a repository can look hardened and be unprotected (the same defect §2 describes);
- 12.1's "bounded file reads … `~/.npmrc`" cannot answer the quarantine question and should not be
  listed for R4 (registry/auth only).

### F4 — R8 (8.2) and 12.1: "for each line matching `uses:`" is not implementable as written

E6 (§7.1) measures, on two purpose-built samples: a `- uses:`-anchored regex finds **zero** of the
real steps; a loose `^\s*(?:-\s*)?uses:` regex yields 3 false positives (block-scalar content,
`with:`-map key, folded `>-`) and misses flow-style step maps, with comment tails, quotes and
`docker://` refs arriving as raw unquoted strings. R8 must be stated against the structural reader
already promised in revision 2 (`src/lib/workflows.js`, §14) with the shape list of §7.2, and the
"unparseable → `skip`" contract must cover flow maps, anchors and block scalars. R9's job-level
`if:` needs the same reader at **job** scope, not step scope.

### F5 — 12.1 probe mechanics (E7): the `%ComSpec%` fallback only works with `windowsVerbatimArguments` and doubled quotes; `pnpm.exe` is not next to the shim

The text "spawns `%ComSpec% /d /s /c` with an explicitly quoted, fully resolved path" is
under-specified and, implemented literally with `spawnSync`, **fails** (status 1, `""C:\…\pnpm.cmd""`
not recognized) because Node re-escapes the argument. It works only with
`windowsVerbatimArguments: true`, and a path containing a space additionally needs the doubled form
`""<path>" <args>"`. `shell:true` is not a safe fallback either (spaced paths break; `DEP0190`). And
because `…\pnpm\bin\` has no `pnpm.exe`, "prefers the `.exe` when one exists" needs an explicit
discovery rule (read the shim's `%~dp0\..\global\v11\<hash>\node_modules\@pnpm\exe\pnpm.exe`, which
is a file read 12.1 does not currently list). Without this, every machine probe on this host returns
`skip`/`error` and R4 silently disappears.

### F6 — R6 (8.2) and 12.1 (E4): the `uses:`-adjacent facts that changed for the **better**, worth pinning

`git ls-files -z -- ':(glob)**/.env*'` works on win32 and matches root and nested `.env` files, so
R6's detection is implementable as written; but it also matches `.env.example`, so the documented
template exclusion list is mandatory, and the `:(glob)` magic is required (plain `**/.env*` skips the
root file). `git check-ignore --no-index --stdin -z` honors negations and nested ignore files, so
R7's behavioral detection is sound — with one trap to write into R7/12.1: **do not pass `-v`**, since
a negation match then returns exit `0` and prints the negation pattern, inverting the verdict.

### F7 — 4.1 and 8.3 (E5): `frozen-lockfile` really is the CI default

`CI=true` alone makes `pnpm install` frozen (`ERR_PNPM_OUTDATED_LOCKFILE`, exit `1` on a stale
lockfile; exit `0` and "Lockfile is up to date" on a consistent one). A workflow that only runs
`pnpm install` is not a finding, and `ci-no-safety-overrides` does not need promoting for this
reason. New, adjacent observation worth recording in R4's docs: under `CI=true` pnpm also runs the
"lockfile passes supply-chain policies" verification, which is what produces
`ERR_PNPM_MINIMUM_RELEASE_AGE_VIOLATION` when a policy is configured (F2).
