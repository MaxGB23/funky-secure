# Paths and guards — the pin's commit, the coexistence error, and the guard both managers read

Source: the owner's report of two observations from an agent he ran himself (L1), plus the decisions he
took across three messages (L2-L4). The three defects are all in *paths*, not in rules: a commit whose
message does not name what it carries, a rule whose message contradicts its severity, and a guard the
tool reads but never writes.

## Specs

S1. The pin gets a commit of its own, and its message names it. The owner, verbatim:

> el paso 8 es el commit que contiene el pin. No hay un commit dedicado a "pin" en este flujo de 9 pasos; el pin --apply del paso 4 queda en el working tree y se commitea recién en el paso 8. Si alguien se detiene entre los pasos 4 y 8, tiene el árbol sucio sin saber por qué.

  The state after `pin --apply` is closed by a step of its own, immediately after the resolve that
  re-syncs the lockfile, and the closing commit of `start` no longer stages `package.json` for the pin.

S2. `init --apply` writes `devEngines.packageManager` when it writes `packageManager`. The owner, verbatim:

> 1. init --apply debería escribir devEngines.packageManager con onFail: "error" cuando escribe packageManager. Es una línea y cierra el hueco exacto del path npm→pnpm, que es tu primer caso de uso.

  **Deviation, decided in L4 after measurement:** the field is written **without** `onFail`. Writing
  `"error"` breaks pnpm's own version auto-switch (measured, RFC 0030), while npm already treats the
  absent value as `error` (measured). Omission is the only value both managers read the way the guard
  needs them to.

S3. `foreign-lockfile` fails when the foreign lockfile coexists with `pnpm-lock.yaml`. The owner, verbatim:

> 2. foreign-lockfile a error cuando coexiste con pnpm-lock.yaml. Hoy el texto miente sobre su severidad. Es tu última red y está abierta.

  A foreign lockfile alone stays `warn`: the product recommends pnpm (G4), it does not require it. Two
  trees is a different state, and it is the one the message already describes as breaking CI.

S4. A finding's severity matches the sentence it prints. The owner, verbatim:

> Mensaje de error, veredicto verde. Un npm install accidental no rompe CI.

  With `--fail-on` at its default `error` (§10.5), a `warn` finding never fails a CI that was never
  configured. The message and the verdict must agree about the same state.

S5. The guard's limits are documented, not implied. The owner, verbatim:

> Un límite a documentar: devEngines sólo lo lee npm (probado con 11.13). No verifiqué yarn ni bun.

S6. The bypasses the guard has are documented too. The owner, verbatim:

> npm install --force → EXIT 0, package-lock.json creado

  The `--force` bypass and the machine-level `pmOnFail` override are named in the page a reader reaches
  from the rule, because a guard sold as a wall is worse than no guard.

  and, closing that message: «no quiero que implementes nada, dame un plan para abordar todo, se usarán subagentes principalmente para mantener contexto».

L2: the owner chose, among the options the plan offered: the pin gets its own commit (O1), `foreign-lockfile` fails in coexistence, macOS stays out of the CI matrix and `validation.md` declares it, the scratch repository for `workflow_dispatch` is approved, and the field loop includes the empty-directory scenario. `devEngines` was deferred to a recommendation after measurement.

L3: the owner corrected one fact of the plan — field loops have run on **Windows** only; Linux has only ever run the suite and the self-scan in CI, which is not the same evidence. `docs/validation.md` currently says "Everything above ran on Windows", which is both stale (the CI matrix runs `ubuntu-24.04`) and imprecise about what CI does and does not cover.

L4 (decision, T3/S2): the measurement reversed the owner's own proposal. `onFail: "error"` makes pnpm refuse the version switch it performs by itself: pnpm 11.28.10 against a repository pinned to 12.3.4 exits 1 with "This project is configured to use 12.3.4 of pnpm", while the same manifest with no `onFail` (and with no `devEngines` at all) exits 0 having re-executed as 12.3.4. npm's own default is already `error`: with no `onFail`, `npm install` exits 1 `EBADDEVENGINES` and writes no `package-lock.json`; with `onFail: "warn"` it exits 0 and writes one. So the field is written without `onFail`, and the owner approved that recommendation («devEngines con tu recomendacion»).

L5 (out of scope, each needs its own record): the conflicted `init --apply` exit code, the `packages:` negation policy, and the renderer's double blank line stay where 0027 left them. The negation evidence gathered here is that none of the 17 `pnpm-workspace.yaml` files in the evidence trees on disk uses a negation at all, so a glob matcher written now would be a matcher tested only by hand-written fixtures.

L6 (second-order, measured): on pnpm 11 a `devEngines.packageManager` makes the next resolve record a `packageManagerDependencies` block in `pnpm-lock.yaml`, so `--frozen-lockfile` fails until that resolve runs once. The printed path of `start` already contains it (`pnpm install --lockfile-only` when `pin` applies, `pnpm import` when a foreign lockfile is present); a repository that runs `init --apply` alone and commits needs one install before CI is green, and that sentence belongs to S5's page.

L7 (correction, T6): T3's record named the new writer `W4`, and `W4` is already the `funky-secure.config.json` strict-preset writer in §11.2. The spec and the code use **`W3b`**, following the file-sibling convention the table already applies to `pnpm-lock.yaml` (`W1a`, `W1b`, `W1c`): same file as `W3`, different key, its own plan item. RFC 0030 carries a dated errata rather than a rewritten body, and the Tasks row above is corrected here instead of in the append-only Log.
