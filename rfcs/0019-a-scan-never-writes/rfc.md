# RFC 0019 — a scan never writes

| | |
|---|---|
| **Status** | `implemented` — the version probe runs outside the scanned repository; `tests/read-only.test.js` holds the repository byte-identical. `0.8.4`. |
| **Revision** | 1 |
| **Present contract** | [`docs/spec/scope.md`](../../docs/spec/scope.md) §7.3. |
| **Supersedes** | nothing. It makes 7.3 true where it has been false since the first release. |

## The defect

The tool has said since 0.1 that it "never writes any file, anywhere" (7.3). It did.

`createCollector` ran `pnpm --version` with the scanned repository as the working directory. pnpm 12,
when the project declares `packageManager`, treats any invocation as an occasion to record that manager
in the project's own lockfile: it appends a second document with `packageManagerDependencies` and about
ninety lines of `@pnpm/exe.*`. So `scan`, `scan --scope all`, `scan --scope machine` and `start` all
modified `pnpm-lock.yaml` of the repository they were inspecting.

Isolated by measurement, four runs:

| Run | Result |
|---|---|
| `pnpm --version`, cwd = the repository | `M pnpm-lock.yaml` |
| `pnpm config list --json`, cwd = the repository | clean |
| `pnpm --version`, cwd = a temporary directory | clean |
| `pnpm --version`, cwd = the repository, no `packageManager` declared | clean |

The last row is the condition: the write needs a pinned manager, which is exactly the state this tool
recommends to every repository it bootstraps.

## Why eight releases missed it

Every test asserted what the tool printed. None asserted what it left on disk. The guard that catches
this is two lines — read the bytes, run the command, read them again — and it did not exist in 440 tests.

That is the entire finding: not a hard bug, a missing question. It was found by the first field round
that ran the tool on a repository generated by something other than this tool, which is the argument
`docs/field-loop.md` makes.

## The decision

**A probe that only reads a version runs outside the repository it is inspecting.**

- `pnpm --version` runs with `os.tmpdir()` as its working directory. Reading a version needs no project,
  so standing in the user's directory buys nothing and costs a file.
- `pnpm config list --json` keeps the repository as its working directory, because its whole job is to
  read the project's policy, and it is measured not to write.
- `tests/read-only.test.js` reads the lockfile, the manifest and `git status --porcelain` before and
  after `scan --scope all`, `scan --scope machine`, `scan --scope repo` and `start`, and asserts all
  three unchanged. `--scope repo` is included on purpose: it was already clean, and a guard that only
  covers the broken case stops covering the fixed one.
- A second test asserts the probe's working directory directly, so the guard bites even where pnpm is
  not installed and the integration test cannot fail for its real reason.

## What it costs

The version probe now spawns in a temporary directory. Nothing in the version path depends on the
project — it resolves an executable, runs `--version`, and parses three numbers — so the cost is one
process working directory and no behaviour change.

## Verification

- `scan --scope all`, `scan --scope machine`, `scan --scope repo` and `start` leave the repository
  byte-identical, with a manifest that pins `packageManager`, which is the state that triggered the bug.
- The §7.3 sentence now names the case, so the next reader knows a spawned tool counts.
- Full suite: 445 tests, 444 pass, 0 fail. Self-scan exit 0.

## Alternatives rejected

- **`--config.manage-package-manager-versions=false` on every probe.** It leaves the probe standing in
  the user's directory with a flag that must stay correct as pnpm changes; the working directory does
  not depend on pnpm's behaviour at all.
- **Only the integration test.** It cannot fail on a machine without pnpm, which includes most CI
  runners, so the guard would be silent exactly where it needs to speak.
- **Asserting the probe's arguments instead of its working directory.** The arguments were never the
  problem.
